# PROJECT: TinyOS 1.0 — A REAL x86-64 DESKTOP OPERATING SYSTEM

You are an elite operating-system architect, senior kernel engineer, x86-64 assembly developer, UEFI developer, C systems programmer, graphics engineer, and desktop environment designer.

Your mission is to DESIGN AND BUILD AN ENTIRE OPERATING SYSTEM FROM SCRATCH.

The project is called **TinyOS 1.0**.

It must be a genuine, native, bootable x86-64 operating system with its own kernel, hardware abstraction, memory management, process isolation, filesystem, device drivers, graphical desktop, and native applications.

This is NOT a browser-based operating system simulation.

This is NOT an HTML/CSS/JavaScript desktop.

This is NOT a Linux distribution.

This is NOT a graphical application pretending to be an operating system.

It must boot independently inside QEMU through UEFI firmware.

# 1. START FROM ZERO — NEW ARCHITECTURE

Build a new operating-system architecture from scratch.

Do not simply extend the existing 32-bit TinyOS kernel.

The existing TinyOS source code can be inspected for reference, but the new implementation must use a clean x86-64 architecture.

Preserve the original project in a backup directory before making substantial changes.

Establish a clean project structure with independent kernel, bootloader, architecture, driver, filesystem, userspace, and desktop components.

Use:
- C for the kernel and system components.
- x86-64 assembly for low-level CPU initialization and context switching.
- UEFI for booting.
- A documented executable and object-file format.
- A modular architecture.

Avoid unnecessary dependencies.

# 2. NATIVE UEFI BOOT

TinyOS must support native UEFI boot on x86-64.

Requirements:

- Build a UEFI-compatible bootloader.
- Generate a valid EFI executable.
- Use the UEFI Boot Services to initialize the machine.
- Obtain the framebuffer through UEFI GOP.
- Obtain the memory map through UEFI.
- Read the ACPI tables when available.
- Load the TinyOS kernel into its intended physical and virtual memory locations.
- Exit UEFI Boot Services correctly.
- Transfer control to the x86-64 kernel entry point.

Create a bootable ISO with the standard UEFI removable-media boot path:

EFI/BOOT/BOOTX64.EFI

Also provide a QEMU-compatible OVMF configuration.

Do not assume that a BIOS bootloader is sufficient.

The kernel must continue independently after UEFI Boot Services have been exited.

- Device driver framework.

Implement proper page-table management and memory protection.

Support supervisor and user memory permissions.

Handle CPU exceptions gracefully instead of silently crashing.

Provide a kernel panic screen with useful debugging information.

# 4. RING 0 AND RING 3 — REAL PRIVILEGE SEPARATION

This is a mandatory architectural requirement.

Implement genuine CPU privilege separation.

## Ring 0

Ring 0 is reserved for the TinyOS kernel.

It handles:
- Hardware access.
- Interrupts.
- Memory management.
- Scheduling.
- Process management.
- System calls.
- Device drivers.
- Filesystem kernel interfaces.

## Ring 3

Ring 3 is reserved for userspace applications.

Native applications must run in unprivileged CPU mode.

Applications must not directly access kernel memory or hardware.

Implement:

- User-mode execution.
- User-mode stack initialization.
- Per-process address spaces.
- Kernel/user memory protection.
- Safe transitions between Ring 3 and Ring 0.
- System call entry and return.
- Process termination.
- Process isolation.

Use an appropriate x86-64 system call mechanism, such as SYSCALL/SYSRET, with correct privilege and register handling.

Configure the required CPU MSRs and kernel entry stack correctly.

Implement a well-defined syscall ABI.

Examples of system calls:

- write
- read
- open
- close
- create
- delete
- allocate
- free
- spawn
- exit
- sleep
- get_time
- get_process_info
- window_create
- window_destroy

Do not implement fake Ring 3 by merely labeling kernel functions as userspace applications.

Demonstrate actual execution at CPL 3.

Create a small native userspace test application that invokes a system call and returns to Ring 3 successfully.

# 15. IMPLEMENTATION STRATEGY

This is a large project. Work incrementally and prioritize a functioning architecture over superficial feature completeness.

Phase 1 — New x86-64 UEFI bootloader and kernel entry.

Phase 2 — CPU initialization, GDT, IDT, TSS, exceptions, interrupts.

Phase 3 — Physical and virtual memory management.

Phase 4 — Ring 3 execution and syscall interface.

Phase 5 — Processes, threads, and scheduler.

Phase 6 — Device abstraction and virtual storage.

Phase 7 — Filesystem and persistent disk support.

Phase 8 — Graphics subsystem and framebuffer.

Phase 9 — Window manager and desktop compositor.

Phase 10 — macOS-inspired desktop interface.

Phase 11 — Native userspace applications.

Phase 12 — Integration, testing, debugging, and bootable ISO.

At each phase:
- Build the project.
- Run the relevant tests.
- Boot QEMU when appropriate.
- Fix regressions.
- Document architectural decisions.

Do not attempt to implement everything in one giant source file.

Do not create nonfunctional placeholders and report them as completed features.

If a feature cannot be completed, state precisely what remains.

# 16. FINAL GOAL

The final product must be a bootable, standalone x86-64 operating system.

When I start QEMU with OVMF and the TinyOS disk or ISO, I should see a polished macOS-inspired desktop.

I should be able to:
- Launch native applications.
- Open and move windows.
- Use a Dock and menu bar.
- Open Finder.
- Create directories.
- Create and edit files.
- Use Terminal.
- Run independent Ring 3 processes.
- Experience real kernel/userspace privilege separation.
- Save files persistently.
- Restart the machine and find my files still there.

The system must use a real x86-64 kernel running in Ring 0, native userspace applications running in Ring 3, and a genuine UEFI boot process.

**Build TinyOS as an actual operating system, not a visual imitation of one.**
